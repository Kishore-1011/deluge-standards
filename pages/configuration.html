Engineering Manual — Section 5

Configuration Standards & Parameter Isolation

Official corporate engineering standards governing top-level configuration declarations, environment parameter isolation, constant definitions, and zero-hardcoding rules in Zoho Deluge.

Zero Hardcoding Rule

Configurable values must never be scattered throughout function bodies. All business constants, IDs, templates, status strings, and endpoint URLs must be declared together at the top of the function.

5.1 Top-Level Configuration Declaration Policy

Rule

Declare all configuration variables, organization IDs, template IDs, status strings, and URLs together at the very top of the function body before executing any business logic.

Why

Top-level declarations centralize settings, allowing instant updates when promoting code between Sandbox and Production environments without modifying logic.

Example

Good Example
deluge 
map sendInvoiceNotification(string invoiceIdStr)
{
    // TOP-LEVEL CONFIGURATION BLOCK
    ORGANIZATION_ID = "74910293";
    EMAIL_TEMPLATE_ID = "TMPL-901";
    SENDER_EMAIL = "finance@company.com";
    
    // BUSINESS LOGIC STARTS HERE
    emailPayloadMap = Map();
    emailPayloadMap.put("org_id", ORGANIZATION_ID);
    emailPayloadMap.put("template_id", EMAIL_TEMPLATE_ID);
    return executeEmailSend(emailPayloadMap);
}
Bad Example
deluge 
map sendInvoiceNotification(string invoiceIdStr)
{
    // Hardcoded IDs embedded inside logic
    sendmail [ from :"finance@company.com", template :"TMPL-901" ];
}

Checklist

  • Configs top-declared on line 1
  • Zero hardcoded IDs in business logic
  • UPPERCASE constant naming

5.2 Mandatory Configuration Parameter Catalog

Rule

Externalize all system parameters (Org ID, Owner ID, Dept ID, Template ID, Form ID, Status strings, Service URLs, API Keys) into top-level constants or Org Variables.

Why

Hardcoded system IDs break during environment promotions and require searching through lines of code to fix.

Example

Good Example
deluge 
ORGANIZATION_ID = "8992019";
DEPARTMENT_ID = "DEPT-SUPPORT";
DEFAULT_PRICE_LIST_ID = "PL-ENTERPRISE";
API_BASE_URL = "https://api.payments.com/v2";
Bad Example
deluge 
res = invokeurl [ url:"https://api.payments.com/v2/charge?org=8992019", type:POST ];

Checklist

  • System IDs top-declared
  • Environment URLs isolated
  • Org Variables used for shared settings

5.3 Sandbox vs Production Environment Switching Policy

Rule

Use environment boolean flags or Org Variables to switch between Sandbox testing endpoints and Production endpoints dynamically. Code modifications should never be required when deploying across environments.

Why

Manual code edits during production promotion risk deploying test credentials or Sandbox endpoints into live customer environments.

Example

Good Example
deluge 
isProduction = zoho.adminuser.contains("corporate.com");
apiEndpoint = isProduction ? "https://api.paymentgateway.com/v1" : "https://sandbox.paymentgateway.com/v1";
Bad Example
deluge 
// Manually commenting out sandbox URL before production deployment
// apiEndpoint = "https://sandbox.paymentgateway.com/v1";
apiEndpoint = "https://api.paymentgateway.com/v1";

Checklist

  • Dynamic environment flag used
  • Zero manual URL edits before deployment
  • Org Variables used for environment keys
