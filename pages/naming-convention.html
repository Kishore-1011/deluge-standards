Deluge Coding Standards & Conventions

Mandatory corporate engineering rules governing identifier naming, function headers, variable declarations, error isolation, formatting, logging, and null-safe execution in Zoho Deluge.

Mandatory Compliance Rule

Every developer must adhere strictly to these Deluge coding standards. Code containing single-letter variables, unhandled API calls, or missing function headers will be rejected in pull request audits.

2.1 Variable Naming Standard

Rule

Use lowerCamelCase and meaningful variable names that clearly represent the business data they store. Never use single-letter variables (x, y, z) or generic names (data, temp, map1, val).

Why

Meaningful variable names make code self-documenting. Developers can understand variable purpose immediately without tracing execution history.

Example

Good Example
deluge 
string customerName = "Alex Rivera";
string invoiceId = "INV-883019";
decimal invoiceAmount = 1450.50;
Bad Example
deluge 
a = "Alex Rivera";
temp = "INV-883019";
x = 1450.50;

Checklist

  • Camel Case
  • Meaningful variable names
  • No x, y, z, temp, data

2.2 Function Naming Standard

Rule

Function names must begin with an active verb, use lowerCamelCase, and explicitly describe their business objective and target entity.

Why

Active verb prefixes clearly communicate what operation the function performs without requiring inspection of its internal implementation.

Example

Good Example
deluge 
map createInvoice(map requestPayloadMap) { ... }
map syncCustomer(string customerIdStr) { ... }
decimal calculateTax(decimal subtotalAmount, decimal taxRate) { ... }
Bad Example
deluge 
invoiceFunc()
handleData()
sync()

Checklist

  • Active verb prefix (create, update, sync, calculate)
  • Includes target business entity
  • lowerCamelCase

2.3 API Variable Naming Standard

Rule

Use standard API variable names for HTTP headers (headersMap), request payload maps (createInvoiceMap), system responses (crmAPIResponse, booksAPIResponse), and sub-collections (lineItems, lineItem).

Why

Standardized API variable names maintain structural consistency across multi-system integrations, making payload transformations predictable across teams.

Example

Good Example
deluge 
map headersMap = Map();
map createInvoiceMap = Map();
list lineItems = List();
map booksAPIResponse = invokeurl [ ... ];
Bad Example
deluge 
h = map();
inv_data = map();
items_arr = list();
res = invokeurl [ ... ];

Checklist

  • Headers in headersMap
  • Service-prefixed response variables
  • Standard collection naming (lineItems, lineItem)

2.4 Variable Declaration & Initialization Standard

Rule

Explicitly declare variables before use and initialize all Map structures using Map() and List structures using List() before population.

Why

Calling .put() on an uninitialized Map or .add() on an uninitialized List raises a breaking Deluge runtime execution error.

Example

Good Example
deluge 
map paramMap = Map();
list customerIdList = List();
paramMap.put("status", "ACTIVE");
customerIdList.add("CUST-101");
Bad Example
deluge 
myMap.put("key", "value");
myList.add("item");

Checklist

  • Explicit Map() initialization
  • Explicit List() initialization
  • No uninitialized collection access

2.5 Code Formatting & Structure Standard

Rule

Apply 4-space indentation across all code blocks, group related statements into logical sections separated by blank lines, and vertically align multi-line invokeurl parameters.

Why

Clean formatting ensures code structure is easy to scan, allowing developers to trace logic branches and parameters in seconds.

Example

Good Example
deluge 
if(customerIdStr == "" || customerIdStr == null)
{
    responseMap.put("status", "ERROR");
    return responseMap;
}

crmAPIResponse = invokeurl
[
    url :"https://www.zohoapis.com/crm/v3/Contacts/" + customerIdStr
    type :PUT
    connection :"zcrm"
];
Bad Example
deluge 
if(customerIdStr==""||customerIdStr==null){responseMap.put("status","ERROR");return responseMap;}
res=invokeurl[url:"https://www.zohoapis.com/crm/v3/Contacts/"+customerIdStr,type:PUT,connection:"zcrm"];

Checklist

  • 4-space indentation
  • Vertically aligned invokeurl parameters
  • Logical blocks separated by blank lines

2.6 Function Header Standard

Rule

Every function must begin with line 1 containing only the mandatory header comment block: /* Author : Kishore Employee Code : ETC-029 */. Remove Purpose, Dependencies, Connections, Modified Date, and all other metadata.

Why

A simple header establishes script author ownership clearly without bloating code files with metadata that quickly becomes outdated.

Example

Good Example
deluge 
/* Author : Kishore Employee Code : ETC-029 */
decimal calculateDealDiscount(decimal dealAmount)
{
    return dealAmount * 0.10;
}
Bad Example
deluge 
/*==================================================================
 * Author        : Kishore
 * Employee Code : ETC-029
 * Purpose       : Calculates tiered volume discounts for Deals
 * Connections   : zcrm
 * Last Modified : 2026-08-10
 * Revision Hist : v1.0, v1.1
 *==================================================================*/

Checklist

  • Header on line 1
  • Contains Author Name
  • Contains Employee Code
  • No extra metadata

2.7 Commenting Standards

Rule

Comment business logic, compliance rules, and non-obvious algorithms. Never write comments explaining self-explanatory programming syntax.

Why

Comments should explain why a business rule exists, not what standard language syntax does.

Example

Good Example
deluge 
// Apply 15% VIP discount for enterprise accounts over $50k
if(accountTypeStr == "ENTERPRISE" && totalVolumeAmount > 50000)
{
    discountRate = 0.15;
}
Bad Example
deluge 
// Check if account type is equal to enterprise
if(accountTypeStr == "ENTERPRISE")
{
    // Set discount rate to 0.15
    discountRate = 0.15;
}

Checklist

  • Explains business rationale (WHY)
  • No redundant syntax notes
  • Obsolete debug comments removed

2.8 Error Handling & Exception Management Standard

Rule

Every API must validate the response. Handle failures gracefully, return meaningful error maps, and log failures.

Why

Unchecked API responses lead to silent failures and runtime crashes when downstream logic attempts to process missing or null data.

Example

Good Example
deluge 
booksAPIResponse = invokeurl [ ... ];
if(booksAPIResponse.get("code") != 0 || !booksAPIResponse.containsKey("invoice"))
{
    info "Books API Failed : " + booksAPIResponse.get("message");
    errorMap = Map();
    errorMap.put("status", "ERROR");
    errorMap.put("message", booksAPIResponse.get("message"));
    return errorMap;
}
Bad Example
deluge 
booksAPIResponse = invokeurl [ ... ];
invoiceId = booksAPIResponse.get("invoice").get("invoice_id");

Checklist

  • Validates API response status
  • Handles failures gracefully
  • Returns meaningful error map
  • Logs failure details

2.9 Operational Audit & Diagnostic Logging Standard

Rule

Use info only for meaningful business logs (e.g. creation events, sync operations, API failures). Never log debug spam like "Reached Here" or raw map objects inside loops.

Why

Meaningful logs maintain clean execution logs, making production troubleshooting simple and fast.

Example

Good Example
deluge 
info "Invoice Created : " + invoiceId;
Bad Example
deluge 
info "Reached Here";
info response;
info x;

Checklist

  • Meaningful business logs only
  • No "Reached Here" or "test" logs
  • No raw map logging in loops

2.10 Null-Safe Coding & Guard Clauses Standard

Rule

Validate map keys using containsKey(), check list sizes, and verify non-null values before property access or type casting (.toString(), .toLong()).

Why

Invoking .toString() or accessing missing keys on a null object causes an immediate Deluge execution crash.

Example

Good Example
deluge 
customerPhoneStr = "";
if(customerMap != null && customerMap.containsKey("phone") && customerMap.get("phone") != null)
{
    customerPhoneStr = customerMap.get("phone").toString();
}
Bad Example
deluge 
customerPhoneStr = customerMap.get("phone").toString();

Checklist

  • Key validation with containsKey()
  • Null check before .toString() / .toLong()
  • List size verified before index access

2.11 API Response Validation Standard

Rule

Validate API responses by checking Status Code, Mandatory Keys, Error Message Fields, and both Success and Failure conditions before reading payload values.

Why

APIs may return HTTP status 200 while containing internal error codes in the response body payload.

Example

Good Example
deluge 
crmAPIResponse = invokeurl [ ... ];
if(crmAPIResponse != null && crmAPIResponse.containsKey("data"))
{
    dataList = crmAPIResponse.get("data");
    if(dataList != null && dataList.size() > 0 && dataList.get(0).get("status") == "SUCCESS")
    {
        info "CRM Contact Updated : " + customerId;
    }
}
Bad Example
deluge 
crmAPIResponse = invokeurl [ ... ];
recordId = crmAPIResponse.get("data").get(0).get("details").get("id");

Checklist

  • Response map null check
  • Mandatory keys verified
  • Success and failure paths handled
