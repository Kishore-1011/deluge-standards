Engineering Manual — Section 3

Connection Standards & Integration Scopes

Official corporate policy governing OAuth2 service connections, link name standardization, scope consolidations, and credential security across all Zoho applications.

Mandatory Connection Policy

Every Zoho service integration must reuse the single corporate connection link created for that service. Creating ad-hoc, personal, or duplicate connections is strictly forbidden.

3.1 Single Standard Connection Per Service

Rule

Every Zoho service must use a single, standardized, lowercase connection link name (zcrm, zbooks, zinventory, zcreator, zdesk, zsign, zexpense, zanalytics, zmail, etc.).

Why

Standard connection names allow scripts to be shared and deployed across sandbox and production environments without connection link re-binding errors.

Example

Good Example
deluge 
booksAPIResponse = invokeurl
[
    url :"https://www.zohoapis.com/books/v3/invoices"
    type :GET
    connection :"zbooks"
];
Bad Example
deluge 
response = invokeurl
[
    url :"https://www.zohoapis.com/books/v3/invoices"
    type :GET
    connection :"kishore_books_conn_v2"
];

Checklist

  • Lowercase connection names
  • Standard service name used (zcrm, zbooks)
  • No personal connection names

3.2 Connection Scope & Reusability Policy

Rule

Reuse the single shared master connection per Zoho service across all applications. Adding new API scopes to the master connection is required; creating duplicate connections is strictly forbidden.

Why

Centralizing OAuth2 scopes into one connection per service simplifies security management and avoids token proliferation.

Example

Good Example
deluge 
response = invokeurl
[
    url :"https://www.zohoapis.com/crm/v3/Contacts"
    type :GET
    connection :"zcrm"
];
Bad Example
deluge 
res1 = invokeurl [ ... connection :"zcrm_sales" ];
res2 = invokeurl [ ... connection :"zcrm_support" ];

Checklist

  • Single connection per service
  • Master connection reused
  • No duplicate parallel connections

3.3 OAuth Scope Minimization & Token Isolation Policy

Rule

Connections must be granted only the minimum required OAuth2 scopes necessary for intended integration features. Never grant full administrative or destroy/delete permissions unless explicitly mandated by security architecture review.

Why

Over-privileged connections expose the corporate tenant to severe data loss or unauthorized modifications if a connection token is compromised.

Example

Good Example
deluge 
// Connection 'zbooks_read' restricted to read-only scopes
// OAuth Scopes: ZohoBooks.invoices.READ, ZohoBooks.contacts.READ
booksResponseMap = invokeurl
[
    url :"https://www.zohoapis.com/books/v3/invoices"
    type :GET
    connection :"zbooks_read"
];
Bad Example
deluge 
// Unrestricted super-admin connection with ALL scopes
responseMap = invokeurl [ ... connection :"zoho_admin_all_permissions" ];

Checklist

  • Principle of Least Privilege applied
  • Read-only scopes for query-only functions
  • No unneeded admin/delete scopes
